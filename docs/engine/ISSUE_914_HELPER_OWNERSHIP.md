# Issue #914: helper ownership investigation

This is a source-level investigation of four similarly named/implemented helpers at the verified `origin/main` revision `f1832384993edaa3223c56637faaa168861eb961`. No runtime change is justified by the evidence below.

## Findings

| Pair | Evidence | Decision |
| --- | --- | --- |
| `pos_in_range` in `info/src/position.rs:83` and `validation/src/position.rs:159` | Both implement inclusive `SourceRange` containment, including any column on an interior line. `info` accepts a `SourcePos`; validation accepts `(line, col)` and builds a `SourcePos`. The validation helper has explicit boundary and multiline tests (`validation/src/position.rs:1196`). Both crates depend on `cwtools_parser`, but neither can call the other's private helper. | Keep the local copies for now. A shared `SourceRange` containment method in `parser` is conceivable, but it would add a parser API for two small uses without a correctness or measured maintenance benefit. If centralizing later, preserve inclusive endpoints and the validation edge-case tests. |
| `valueclause_bodies` in `lsp/src/semantic.rs:578` and `validation/src/position.rs:1105` | Both flatten `RuleType::ValueClauseRule` bodies and clone the contained `(RuleType, Options)` values. LSP's `documentlink.rs:156` consumes the owned vector to traverse rules; validation consumes it during cursor classification (`position.rs:679`, `1065`). `cwtools_rules` owns `RuleType`, but a common helper there would create a new public cross-crate API for this one operation. | Keep the copies. The implementation and ownership needs are already aligned; centralizing is a small deduplication with public API cost and no behavior gain. |
| `with_leaf_value_str` in `index/src/lib.rs:82` and `validation/src/common.rs:280` | Both preserve text values and format floats, integers, and booleans, but their fallback behavior differs: index maps clauses to `""`, while validation maps them to `"{...}"` through `leaf_value_to_string`; both map unresolved string ids to `""`. Callback timing also differs: `StringTable::with_string` invokes its closure while holding a shard or overlay read lock (`string_table/src/string_table.rs:408`). Index passes its callback through while that lock is held. Validation copies the text into `SmallVec<[u8; 64]>` inside the lock, releases the lock, then invokes the caller's callback on the scratch text. | Keep both. The fallback behavior is already observably different, and changing callback timing or copying behavior during unification could affect lock contention, reentrancy, and allocation costs. Keep the one-line index-helper comment stating that its callback runs under the `StringTable` read lock and must not re-enter the table. |
| `localisation_paths` in `lsp/src/scan/loc.rs:15` and `driver/src/lib.rs:1079` | Both call `driver::discover_localisation_files`, log discovery failures, filter to `FileKind::Localisation`, and return paths. The LSP logs per-path failures and overall failure through `tracing::warn!`; the batch driver uses `eprintln!` and distinguishes warning from error. Their callers belong to different front ends with different logging contexts. | Keep both wrappers. The shared discovery API already owns filesystem policy; preserving caller-specific diagnostics is more useful than moving this thin frontend adaptation into another shared API. |

## Scope and verification

This investigation makes no runtime behavior changes. The findings were checked against the source at the verified base commit above, and `git diff --check` passes. Tests and diagnostics guards were not run because the change only documents helper ownership and callback lock scope.
